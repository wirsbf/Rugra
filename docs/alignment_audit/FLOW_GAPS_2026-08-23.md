## 0. 结论摘要(TL;DR)

1. **ROADMAP 〇节(2026-07-04)的声明已过时**。`ALIGNMENT_ROADMAP.md:66` 声称
   "FlowInfo 范式确实 L1(无忠实移植),Rugra 用线性扫描 + 离线 CFG 分割替代"。实际上
   src/flow.rs 是一个 2756 行的 FlowInfo 部分移植(可达性 work-list、visited 图、
   setFallthruBound/fallthru、xrefControlFlow、generateBlocks 五步全在),且**已接入主管线**:
   `bin/rugra.rs:246`、`examples/curl_decompile.rs:1362`、`examples/getstr_stage_snapshot.rs:617`
   都调用 `rugra::flow::follow_flow`。git 史:flow.rs 自 2026-07-22 起大规模移植
   (`4fe0b2e`/`1f64d10`/`a423f88`),2026-08-13 接入 SLEIGH 单 translator(`ef36d66`)。
2. **5 个子系统的真实状态**("缺失"声明部分过时):
   - (1) 可达性流追踪: **已移植并接线**(残留:override/异常语义/checkContainedCall/入口副作用,
     httpd 门禁仍走线性扫描)。
   - (2) 跳转表流内展开: **部分存在**(generate_ops 确实展开表目标并继续追踪),但恢复本体
     走 in-place `try_recover`,缺 partial 克隆简化,失败不 truncateIndirectJump。
   - (3) 截断流/partial Funcdata 克隆(truncatedFlow): **完全缺失**(无 `Funcdata::truncatedFlow`、
     无 FlowInfo 克隆构造器)。
   - (4) 子函数内联: **结构性 stub**(`inlineSubFunction` 内 `let res = -1i32;` 硬编码,
     flow.rs:1658,永不成功;`Funcdata::inlineFlow` 无对应物)。
   - (5) 流内 P-code 注入: **结构性 stub**(doInjection 等 4 函数已移植但要求调用方提供
     pre-emitted ops;`generate_ops` 从不调用 `injectPcode`;CALLOTHER 不入 injectlist)。
3. **最重依赖链**: `stageJumpTable 的 truncatedFlow partial 克隆 → jumptable 恢复质量 →
   BRANCHIND 目标展开 → switch 语句结构化`。这正是已登记的 `JUMPTABLE-PIPELINE-0001`(TODO_BOARD.md:50)。

## 3. 五个子系统判定与影响面

### 3.1 子系统 (1):可达性流追踪 — 判定:**已移植并接线(不再是缺失项),残留缺口 6 项**

已具备:addrlist LIFO work-list、visited(BTreeMap)VisitStat、setFallthruBound 的
upper_bound+前驱步语义、reinterpreted 检测、Const-space 相对分支(findRelTarget)、
xrefControlFlow 的 maxtime/deleteRemainingOps、artificialHalt 四类、fillinBranchStubs、
collectEdges→splitBasic→connectBasic→entry-guard→removeUnreachableBlocks。
oracle 证据:SLEIGH-FLOW-REL-0001 `MATCH records=388 ops=81 relatives=33 blocks=34
edges=49`(TODO_BOARD.md:331);FLOW-TARGET-BOUND-0001 `MATCH`(TODO_BOARD.md:241)。

残留缺口(全部当前不可达或降级):
1. `checkContainedCall`(flow.cc:1361)**整函数缺失** — PIC 代码(位置无关构造)中
   "call 到自身函数中段"不会改写为 BRANCH;影响:PIC 目标文件的反编译会把内部分支
   误当外部调用。curl 语料(glibc静态链接、非 PIC 内部跳转模式)未命中。
2. `Override::getFlowOverride/overrideFlow`(flow.cc:415-418,474-475)缺失 —
   用户流覆盖(CALL 改 BRANCH 等)不可用。
3. error_* 标志的 throw 语义降级为 eprintln(flow.rs:482-485,510-512)— Ghidra 在
   inlineFlow 路径设置 error_outofbounds|error_unimplemented|error_reinterpreted
   (funcdata_op.cc:864-865)依赖 throw 提前终止,Rugra 降级后 inline 语境无法正确中止。
4. 入口副作用缺失:follow_flow 后 `size`/`blocks_generated`/`unimplemented_present`/
   `baddata_present`/`switchOverJumpTables` 全部未设置(funcdata_op.cc:772-782 vs
   flow.rs:2675-2682)。
5. `insn_max=100000` 硬编码而非 Architecture 选项(flow.rs:318)。
6. httpd 门禁与 debug_cfg 等旧路径仍走 inject_raw_ops 线性扫描
   (httpd_decompile.rs:261,debug_cfg.rs:87)— 两条门禁输入路径不一致。

### 3.2 子系统 (2):跳转表流内展开 — 判定:**部分存在,恢复链错位**

存在的部分:generate_ops 第二阶段确实把恢复出的表目标 `new_address` 进 work-list 并
继续 `fallthru()`(flow.rs:2082-2132 ↔ flow.cc:796-811 结构对应);BRANCHIND 的
collectEdges 逐表项建边(flow.rs:882-915 ↔ flow.cc:933-957)。

缺口(按严重度):
1. **恢复本体错位**:Ghidra 的恢复 = `recoverJumpTables → data.recoverJumpTable(partial,op,this,mode)
   → stageJumpTable → partial.truncatedFlow + "jumptable" 动作组简化 → recoverAddresses`
   (flow.cc:1442,funcdata_block.cc:497-537)。Rugra 主管线 = `jumptable::try_recover`
   **在原函数上**恢复(flow.rs:2108,jumptable.rs:4137-4156,注释明言"collapsed into a
   single call because Rugra does not yet clone a partial Funcdata")。partial 克隆简化的
   作用是把 SWITCH 变量计算链上的 dead code/无关分支清掉再做围栏分析——in-place 恢复
   会被未简化 IR 干扰,恢复率低于 oracle。已登记:JUMPTABLE-PIPELINE-0001(TODO_BOARD.md:50)。
2. **失败无降级**:Ghidra 恢复失败 → `truncateIndirectJump(op,mode)`(flow.cc:1444-1445)
   把 BRANCHIND 变 CALLIND/RETURN 并补人工 halt;Rugra 静默跳过(flow.rs:2108-2116 无
   else 分支)→ 失败的 switch 留下无边 BRANCHIND,下游 blockaction 只能丢弃或断流。
3. **notreached/multistage 缺**:`jt->isPartial()` 的 notreached 延迟重试
   (flow.cc:1447-1455)与 `checkMultistageJumptables`(flow.cc:1408-1417,Rugra 空壳
   flow.rs:738-751)缺 → 多级跳转表(表项本身是跳转)不收敛。
4. **恢复时机错位**:ActionSwitchNorm 里还有第二个恢复入口
   `crate::jumptable::recover_jump_tables(fd)`(coreaction.rs:2560,自创 pre-pass)——
   Ghidra 的恢复全部在流内完成,ActionSwitchNorm 只做 matchModel/recoverLabels/
   foldInNormalization(coreaction.cc:4548)。双入口+不同时机会造成
   流内与动作期内恢复结果不一致。
5. **switchOverJumpTables 空转**(funcdata.rs:7525-7529)→ 块索引/default 块不计算 →
   `installSwitchDefaults`(funcdata.rs:2332)无 default 边可装。

影响面:凡含间接跳转(switch/跳表/thunk 表)的函数:目标块展开(部分在)、CFG 边
(部分在)、switch 结构化(ActionSwitchNorm 数据不足)、default case(缺)、
多级表(缺)。**curl 语料恰好多数 switch 经 try_recover 可恢复或无 switch,故门禁绿;
这不是等价性的证明。**

### 3.3 子系统 (3):截断流/partial Funcdata 克隆 — 判定:**完全缺失**

无 `Funcdata::truncatedFlow`、无 FlowInfo 克隆构造器(flow.cc:52)、stage_jump_table
文档化跳过(funcdata.rs:7268-7271)。这是 **jumptable 恢复链的地基**(Ghidra 在
partial 上跑 `allacts.setCurrent("jumptable")` 全动作组,funcdata_block.cc:499-512),
也是 inline 的前置(inlineFlow 同样克隆语义)。连带缺失:obank uniqId 跨函数接力

## 4. "等价替代"声明评估(curl 语料边界)

**ROADMAP 〇节声明的"对普通函数功能等价(curl 24/24)"在当前代码形态下应重述为**:
"可达性追踪已移植;对 curl 语料(无 inline 属性函数、无 callfixup、无 CALLOTHER fixup、
switch 少且 try_recover 可恢复、无 PIC 自调用)与 Ghidra 输出可比。"

分叉点清单(何时会与 oracle 产生可见差异):

| 触发条件 | 分叉机制 | 首个失效子系统 |
|---|---|---|
| 函数含 `always_inline` callee / 编译器 intrinsic 展开 | CALL 不被替换为内联体,输出多余 call + 参数复制 | (4) |
| callee 有 callfixup(如 `__x86.get_pc_thunk.ax`) | CALL 原样保留,PC 计算链错误 | (5) |
| switch 的围栏分析在未简化 IR 上失败 | try_recover 返回 None → BRANCHIND 悬空,switch 变 goto/断流(Ghidra 会 truncateIndirectJump 成 CALLIND 至少保形) | (2)+(3) |
| 多级跳转表(表项是跳转指令) | notreached/multistage 缺,表不收敛 | (2) |
| BRANCHIND 恢复失败但 Ghidra 成功(反之亦然) | 无 truncateIndirectJump → CFG 边数不同 → 结构化差异 | (2) |
| PIC:call 目标落在自身函数字节内 | checkContainedCall 缺,误判为子调用 | (1) |
| 指令数 > max_instructions / 坏数据 / offcut 重解释 | 不 throw + 降级日志 → 流截断行为同,但 inline 语境错误继续 | (1) |
| 用户 Override(流程改写/跳表 override) | 全缺 | (1)/(2) |
| httpd 等仍走线性扫描的入口 | 不可达字节被解码(数据/对齐填充进入 IR) | 门禁不一致 |

注意:即便 curl 门禁 defects=0,也只是上述触发条件未被命中的证据;按机制 B2,
flow.rs 整体状态 = **L2(MISMATCH/部分 NO_ORACLE)**,与 SLEIGH-FLOW-0001 的
IN_PROGRESS 判定一致(TODO_BOARD.md:330)。
