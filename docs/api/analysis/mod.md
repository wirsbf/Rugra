## 1. 文档定位

本文件用于说明 `docs/api/analysis/` 这组文档的**历史背景、适用边界与当前可信度**。

它不是对当前 Rugra 主干分析架构的最新权威说明。  
更准确地说，它是对**旧版分析分层文档体系**的一个保留索引，用于帮助开发者识别：

- 这组文档 originally 在描述什么
- 为什么它们会与当前源码结构不完全一致
- 现在继续阅读它们时应注意什么
- 哪些内容可以当作历史参考，哪些内容不能继续当作当前事实

---

## 2. 为什么这是“历史/遗留说明”

早期文档体系曾将 Rugra 的分析流程按一个相对独立的 `analysis/` 目录来组织，并围绕以下主题展开：

- CFG 构建
- 数据流分析
- SSA 构造
- 类型推断
- 变量恢复
- 活跃性分析
- 优化规则
- 高级变量合并

这些主题本身仍然是 Rugra 反编译分析链路中的重要组成部分。  
但**当前主干源码结构**已经不再完全按这种目录划分展开。

从当前可见代码状态看，实际主线更偏向于围绕以下核心对象与模块组织：

- `Funcdata`
- `PcodeOp`
- `Varnode`
- `BlockBasic`
- `Heritage`
- `ActionDatabase`
- `PrintLanguage`
- `PrintC`

也就是说：

> **“分析能力仍然存在于项目目标和部分实现中”**  
> 不等于  
> **“当前仍有一个与旧文档完全对应、稳定存在的 `src/analysis/` 主干目录可作为事实入口”**

因此，本目录下的文档应当被理解为：

- **历史分析架构说明**
- **旧版分层思路的残留文档**
- **帮助迁移理解的参考资料**

而不是：

- 当前主干 API 的唯一来源
- 当前实现状态的精确镜像
- 已经核实与当前源码完全同步的模块索引

---

## 3. 当前阅读这组文档的正确方式

如果你继续阅读 `docs/api/analysis/` 下的文件，请采用以下阅读姿势：

### 可以把它们当作
- 旧版分析分层思路的说明
- 某些分析主题的概念性参考
- 历史实现方向的索引
- 理解项目演化路径的材料

### 不应把它们当作
- 当前 `src/` 真实结构的权威映射
- 当前所有分析接口都已存在的证明
- 当前端到端分析流程已经稳定的证据
- 当前运行时行为已经完成验证的依据

`docs/api/analysis/` 下的文件通常围绕以下主题展开：

- `calls.md`

- `ssa.md`
- `type_inference.md`
- `type_propagation.md`
- `variables.md`
- `rules/` 子目录

这些主题仍然具有概念价值，因为它们反映了 Rugra 试图完成的分析能力谱系。  
但在阅读时必须注意：

1. 它们描述的实现未必仍按同名模块存在  
2. 它们描述的 API 未必仍是当前主入口  
3. 它们描述的流程未必已被当前架构完整恢复  
4. 它们描述的能力未必已经过验证

## 6. 当前可信结论

基于当前文档体系与代码现状，可以较稳妥地给出以下结论：

### 6.1 可以确认的
- Rugra 仍然以分析能力为核心目标之一
- 数据流、SSA、类型、变量恢复等主题仍然是项目的重要方向
- 这些历史文档保留了项目早期或中期的分析分层思路
- 它们对理解“项目原本想怎么分层”仍有参考价值

### 6.2 不能直接确认的
- 当前存在一个完整、稳定、活跃维护的 `src/analysis/` 主干目录
- 本目录下所有 API 文档都与当前源码同步
- 文档中提到的所有分析接口现在都仍然可调用
- 旧架构中的主分析入口仍然是当前推荐使用方式

## 7. 对后续维护者的要求

后续如果继续维护 `docs/api/analysis/`，建议遵守以下规则：

### 7.1 保留“历史”标签
在未逐篇核对前，本目录下的文档应默认视为：

- 历史说明
- 待复核材料
- 概念参考

而不是当前主干权威文档。

### 7.2 若发现内容与当前源码冲突
优先做以下之一：

- 改写为“历史说明”
- 补充“当前状态已变化”的提示
- 在文档开头增加“已过期风险”说明
- 如无保留价值，再考虑删除

### 7.3 若将来恢复明确的分析分层
如果未来 Rugra 再次形成稳定、真实存在的分析模块分层，再重新把本目录改回“当前 API 索引”也不迟。  
但在此之前，不应提前把未来结构写成当前事实。
