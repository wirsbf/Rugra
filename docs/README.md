# Rugra 文档总索引（Docs Index）

本文档是 `rugra/docs/` 目录的统一入口，用于帮助读者快速理解当前文档系统的结构、用途与阅读顺序。

本索引的首要目标不是“把项目描述得更完整”，而是**让文档系统尽量忠实于当前代码状态**，并明确区分：

- 项目目标
- 当前现状
- 已实现能力
- 待验证能力
- 历史文档
- 需要继续修复的失真部分

> **使用原则**
>
> 1. 以 `rugra/src/` 的真实代码为准
> 2. 以总控文档解释当前工程状态
> 3. 若文档之间冲突，优先采信与当前代码更一致、更新更晚、结论更克制的版本
> 4. 若发现失真，应优先修正文档，而不是继续沿用旧说法

---

## 1. 这份索引解决什么问题

当前 Rugra 工程已经积累了较多文档，但历史上存在以下问题：

- 根目录与子项目定位一度混乱
- 部分文档把目标态写成现状
- 部分文档把静态结构对齐写成运行时一致
- 部分 API 文档沿用了旧架构命名
- 某些说明文件虽然存在，但用途边界不够清晰

因此，本文件用于统一回答两个问题：

1. **应该先看哪些文档？**
2. **每类文档分别记录什么，不记录什么？**

## 2. 推荐阅读顺序

如果你第一次进入 `rugra/`，建议按下面顺序阅读：

### 第一步：理解项目定位
1. `../README.md`
2. `../AGENTS.md`

这两份文档用于说明：

- Rugra 是什么项目
- 当前真实工程范围在哪里
- 文档和代码如何同步维护
- 当前不应继续夸大的结论有哪些

---

### 第二步：理解项目结构
3. `PROJECT_STRUCTURE.md`

这份文档回答：

- `src/` 当前真实有哪些模块
- `docs/` 当前有哪些文档分区
- `examples/`、`tests/`、`tools/`、`result/` 各自承担什么职责
- 哪些旧结构描述已经不应继续使用

---

### 第三步：理解当前状态与风险
4. `../CURRENT_STATUS.md`
5. `../GAP_ANALYSIS.md`
6. `../ALIGNMENT_PROGRESS.md`

这三份文档分别回答：

- **`CURRENT_STATUS.md`**：项目现在到底处于什么状态
- **`GAP_ANALYSIS.md`**：与目标能力、与 Ghidra 相比还缺什么
- **`ALIGNMENT_PROGRESS.md`**：哪些只是静态对齐，哪些仍缺运行时验证

---

### 第四步：理解当前任务与验证方式
7. `TODO_BOARD.md`
8. `VERIFICATION_GUIDE.md`
9. `data_contract.md`

这三份文档分别回答：

- **`TODO_BOARD.md`**：现在优先在修什么、补什么
- **`VERIFICATION_GUIDE.md`**：当前验证体系到底做到哪一层
- **`data_contract.md`**：核心数据对象如何在模块间流动、各自承担什么职责

---

### 第五步：按需深入专题
10. `api/`
11. `alignment_docs/`
12. `workflow/`
13. `AgentLog/`
14. 其他专题目录

当你已经掌握全局状态后，再进入专题目录做深入阅读。

## 3. `docs/` 目录结构与用途

下面按目录和文件类型给出用途说明。

---

## 3.1 总控文档

### `PROJECT_STRUCTURE.md`
**用途**：项目结构总览与文档导航  
**适合谁看**：所有进入项目的人  
**主要回答**：

- 当前源码如何组织
- 当前文档如何组织
- 目录级职责怎么划分

**不负责**：

- 详细 API 说明
- 具体算法证明
- 单次会话细节

---

### `TODO_BOARD.md`
**用途**：待办事项与当前优先级看板  
**适合谁看**：准备开始本轮工作的开发者 / AI 助手  
**主要回答**：

- 当前优先修什么
- 哪些问题是 P0 / P1 / P2
- 文档修复是否完成
- 哪些事项应暂缓

**不负责**：

- 详细设计过程
- 历史背景长文解释

---

### `VERIFICATION_GUIDE.md`
**用途**：验证体系说明  
**适合谁看**：做测试、做对齐、做结果判断的人  
**主要回答**：

- 静态对齐和运行时验证有什么区别
- 当前验证框架做到哪一步
- 哪些验证只是框架存在，哪些是真正跑通
- 当前哪些结论还不能宣称

**不负责**：

- 替代测试结果本身
- 直接证明项目已经完全一致

---

### `data_contract.md`
**用途**：核心数据实体与跨模块边界契约  
**适合谁看**：做架构梳理、模块重构、接口调整的人  
**主要回答**：

- `Address`、`Varnode`、`PcodeOp`、`Funcdata` 等对象在系统里承担什么角色
- 数据从二进制解析流到输出阶段时，中间约束是什么
- 哪些层负责底层事实，哪些层负责高层解释

**不负责**：

- 替代源码注释
- 详细 API 手册

---

## 3.2 项目状态文档

这些文档位于 `docs/` 之外，但应与本目录联动阅读。

### `../CURRENT_STATUS.md`
**用途**：当前状态的可信描述  
**主要回答**：

- 项目现在最真实的状态是什么
- 当前哪些能力可以确认
- 当前哪些结论不能夸大

---

### `../GAP_ANALYSIS.md`
**用途**：能力差距分析  
**主要回答**：

- 与 Ghidra 相比缺什么
- 当前在变量恢复、控制流结构化、类型推断、输出质量等方面有哪些短板

> 注意：这份文档更偏“差距与方向”，不是“状态宣告”。

---

### `../ALIGNMENT_PROGRESS.md`
**用途**：对齐进度分层记录  
**主要回答**：

- 哪些对象只完成了静态结构对齐
- 哪些行为仍待运行时对拍
- 哪些结论不能写成“已完成一致性”

---

## 3.3 API 文档目录

### `api/`
**用途**：源码模块与公开接口的参考说明  
**适合谁看**：

- 阅读 `src/` 的开发者
- 需要理解 Rugra 核心对象的人
- 正在修接口、补文档的人

**建议阅读方式**：

1. 先看 `api/README.md`
2. 再看核心对象：
   - `address.md`
   - `varnode.md`
   - `op.md`
   - `pcoderaw.md`
   - `block.md`
   - `funcdata.md`
3. 然后看流程相关：
   - `heritage.md`
   - `action.md`
   - `coreaction.md`
   - `ruleaction.md`
   - `blockaction.md`
4. 最后看输出与扩展：
   - `printlanguage.md`
   - `printc.md`
   - `binary/`
   - `disasm/`
   - `align/`

### `api/` 的使用边界
API 文档的作用是：

- 解释模块职责
- 补充接口语义
- 辅助理解源码

API 文档**不应被当成**：

- 当前运行时能力证明
- 完整产品功能清单
- “已经和源码 100% 同步”的自动真相源

如果 `api/` 与 `src/` 冲突，应先修 API 文档。

## 3.4 会话记录目录

### `AgentLog/`
**用途**：工程会话日志  
**适合谁看**：

- 想知道上一轮会话做了什么的人
- 想理解近期文档或代码为何被修改的人

### `AgentLog/TEMPLATE.md`
**用途**：日志模板  
**要求**：

- 记录本次改动做了什么
- 记录哪些文档同步更新了
- 记录下一步工作切入点
- 不把未经验证的成果写成“最终完成”

### 阅读建议
当你想继续上一轮工作时：

1. 先看最近一篇日志
2. 再对照 `TODO_BOARD.md`
3. 再去看对应代码或对应文档

---

## 3.5 对齐文档目录

### `alignment_docs/`
**用途**：更细粒度的 Ghidra 对齐资料  
**适合谁看**：

- 正在做 Ghidra 概念映射的人
- 需要记录类、方法、结构差异的人
- 需要沉淀更细的对齐说明的人

**适合存放的内容**：

- 对象映射表
- 字段对照
- 操作码或语义对照
- 某类验证差异的长篇说明

**不适合存放的内容**：

- 总体状态判断
- 日常待办列表
- 会话日志

## 4. 文档类型与“可信度边界”

为了降低失真，阅读文档时建议按下面方式理解其可信边界。

### A 类：总控事实文档
包括：

- `PROJECT_STRUCTURE.md`
- `TODO_BOARD.md`
- `VERIFICATION_GUIDE.md`
- `data_contract.md`
- `../CURRENT_STATUS.md`
- `../ALIGNMENT_PROGRESS.md`

这类文档应尽量：

- 克制
- 可核对
- 明确边界
- 少写夸张结论

---

### B 类：专题解释文档
包括：

- `api/`
- `alignment_docs/`
- `method/`
- `src_ref/`

这类文档更适合：

- 解释
- 展开
- 对比
- 总结

但也更容易因为代码变化而过期，所以要经常回看。

---

### C 类：过程记录文档
包括：

- `AgentLog/`
- `experiments/`
- `decisions/`
- `branches/`

这类文档主要回答：

- 当时做了什么
- 为什么这么做
- 结果如何
- 下一步是什么

它们不应直接被当成“当前状态的唯一事实依据”，需要和总控文档一起看。

## 5. 文档修复后的推荐维护原则

后续维护 `docs/` 时，建议统一遵循以下原则：

### 5.1 不把目标态写成现状
例如：

- 计划中的能力，不写成已支持
- 框架存在，不写成已稳定运行
- 少量样本成功，不写成全面完成

---

### 5.2 不把静态结构对齐写成运行时一致
例如：

- 有 `align` 模块，不等于与 Ghidra 行为一致
- 有 `runtime_verify.rs`，不等于对拍体系已打通
- 有输出示例，不等于端到端质量已完成验证

---

### 5.3 不把 README 当产品宣传页
README 首先应解释真实项目状态，而不是只写理想愿景。

---

### 5.4 文档索引必须能导航
一份好的总索引至少要回答：

- 看整体去哪里
- 看状态去哪里
- 看 API 去哪里
- 看验证去哪里
- 看历史记录去哪里

---

### 5.5 代码变化要联动文档变化
以下情况发生时，应同步检查并更新文档：

- 新增/删除/重命名 `src/` 模块
- 调整公共接口
- 修改 `Funcdata` / `PcodeOp` / `Varnode` 等核心对象含义
- 改变 CLI 状态
- 改变验证口径
- 增加或废弃重要样例

## 7. 当前最重要的提醒

如果你在阅读 Rugra 文档时只记住一件事，请记住这句：

> **当前文档系统的目标是“减少失真”，不是“制造完成感”。**

因此：

- 如果某个文档写得很乐观，请去看状态文档和代码
- 如果某个文档写得像已全部完成，请检查是否有测试或验证依据
- 如果多个文档冲突，请优先修正冲突，而不是继续引用旧说法

---

## 8. 结语

这份 `docs/README.md` 的作用，是把修复后的文档系统重新组织成一个**可读、可导航、可持续维护**的入口。

后续如果文档目录继续增长，这份索引应始终保持三个特性：

1. **真实**：不替代码做夸张背书  
2. **清晰**：让读者知道该去哪里找信息  
3. **可维护**：当结构变化时能同步更新而不失真  

如果你发现本索引与当前目录或代码状态不一致，应优先更新本文件，并同步检查：

- `PROJECT_STRUCTURE.md`
- `TODO_BOARD.md`
- `api/README.md`
- `VERIFICATION_GUIDE.md`
